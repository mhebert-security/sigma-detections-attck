# sigma-detections-attck

> Rules that say what they caught.

A detection rule is only as trustworthy as the framework that names what it catches. Every Sigma rule here maps to a MITRE ATT&CK technique, so a hit answers which stage of an intrusion it belongs to. Rules are tested against real adversary telemetry generated by Atomic Red Team in a home SOC lab before they ship. Naming the part of the kill chain is how a single alert becomes a story an analyst can act on.

---

## Architecture

```
Windows EC2  ──Sysmon──►  Wazuh Manager (AWS)  ──alerts──►  This Repo
   ▲                              │
   │ Atomic Red Team           rules/        ← Sigma YAML (canonical)
   │ (adversary telemetry)     wazuh/        ← Wazuh XML (deployment)
   └──────────────────────     tests/        ← Validation evidence
                               docs/         ← ATT&CK coverage matrix
```

**Log sources:** Windows Event Logs, Sysmon (olafhartong modular config)
**Detection platform:** Wazuh
**Telemetry generation:** Atomic Red Team
**Rule format:** Sigma (portable) + Wazuh XML (deployed)

---

## Quality Gate

A rule ships when three conditions are met:

1. **Sigma rule written** — correct `logsource`, ATT&CK `tags`, detection logic, and false-positive assessment
2. **Wazuh XML translated** — field names verified against actual Wazuh-parsed Sysmon events
3. **Atomic test fired and caught** — the matching Atomic Red Team test was executed, Wazuh alerted, and evidence is logged in `tests/`

Rules that have not passed all three gates carry `status: experimental`.

## Rule Naming Convention

Files are named by detection subject, not technique ID. The ATT&CK ID lives inside the rule's `tags` field.

```
proc_create_powershell_encoded_command.yml   ✓
T1059_001.yml                                ✗
```

One technique can have multiple rules. One rule covers one detection pattern.
